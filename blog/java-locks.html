深入理解 Java 锁机制：
从 synchronized 到 ReentrantLock

锁不是为了“让代码变慢”，而是为并发访问建立一套可证明的秩序。本文从一个丢失更新问题出发，逐层拆开 JVM 内置锁、JUC 显式锁、AQS 与 CAS，并把它们落到后端工程中的选型上。

发布于 2026-10-14 约 28 分钟阅读 Java · JUC · AQS · CAS
版本说明

除特别说明外，文中 API 适用于 Java 8 及以上版本。对象头、锁优化和 AQS 队列的描述用于建立概念模型；涉及 JVM/JDK 内部实现时会标出版本边界，不应把某一版本源码当作 Java 规范。

1. Java 锁机制概述

多线程本身并不会制造错误。问题发生在多个线程同时读写共享的可变状态，而程序又没有规定这些访问之间的顺序。下面的计数器看似执行了 200,000 次自增，结果却可能更小：

public class UnsafeCounterDemo {
    private static int count = 0;

    public static void main(String[] args) throws InterruptedException {
        Thread t1 = new Thread(() -> increment(100_000));
        Thread t2 = new Thread(() -> increment(100_000));
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println(count); // 可能小于 200000
    }

    private static void increment(int times) {
        for (int i = 0; i < times; i++) {
            count++; // 读取、加一、写回：不是一个不可分割的动作
        }
    }
}

count++至少包含“读取旧值、计算新值、写回”三个逻辑步骤。两个线程可能读取同一个旧值，各自加一后又写回同一个新值，于是一次更新被覆盖。这就是竞态条件；访问共享状态且必须作为整体保护的代码范围称为临界区。

并发正确性的三个维度

01

原子性

一个操作或一组操作要么全部完成，要么外部看不到中间状态。互斥锁常用来扩大原子操作的边界。

02

可见性

一个线程修改共享变量后，其他线程能按 Java 内存模型规定及时观察到结果。

03

有序性

编译器与处理器可以重排序，但不能破坏 happens-before 关系对程序员承诺的观察结果。

2. synchronized：JVM 内置的互斥协议

synchronized最重要的优点不是语法短，而是锁的获取与释放由 JVM 保证。只要所有线程都使用同一个监视器对象保护同一份状态，临界区就能获得互斥与内存可见性。

三种写法，三种锁对象

同步实例方法锁定当前对象 this，静态同步方法锁定对应的 Class 对象，同步代码块则锁定括号中显式指定的对象。

public class AccountService {
    private final Object balanceLock = new Object();
    private int balance;

    // 锁是当前实例 this；不同实例之间不互斥
    public synchronized void deposit(int amount) {
        balance += amount;
    }

    // 锁是 AccountService.class；所有实例共享
    public static synchronized void refreshGlobalConfig() {
        // ...
    }

    // 锁是显式指定的 balanceLock，保护范围更清楚
    public int getBalance() {
        synchronized (balanceLock) {
            return balance;
        }
    }
}
锁住的不是代码

synchronized关联的是对象监视器。两段完全不同的代码，只要同步在同一个对象上就会互斥；同一段代码如果在不同对象上同步，也不会彼此阻塞。锁对象应保持稳定，通常使用 private final 字段，避免锁住字符串常量、装箱对象或可能被外部代码拿到的对象。

可重入、原子性与可见性

内置锁是可重入的：线程持有某对象的监视器后，可以再次进入该对象保护的同步方法，而不会把自己锁死。运行时会记录持有线程与重入次数，退出一次只减少一层计数。

互斥保证同一时刻只有一个线程执行临界区，因此一组操作可以作为整体完成。Java 内存模型还规定：对一个监视器的解锁 happens-before 随后对同一监视器的加锁。退出同步块前的写入，会对之后成功获得同一锁的线程可见。这同时限制了会破坏该关系的重排序。

monitorenter、monitorexit 与 Monitor

同步代码块编译后通常能看到 monitorenter 与 monitorexit 字节码。正常路径和异常路径都会生成退出监视器的逻辑，所以即使临界区抛出异常，JVM 也会释放锁。同步方法一般通过方法访问标志 ACC_SYNCHRONIZED 表示，而不是简单地在方法体里插入这两条指令。

对象头与锁状态：必须带上版本前提

在 HotSpot 的一些早期版本中，普通对象头包含 Mark Word，运行时会在其中编码哈希、GC 年龄以及与锁相关的信息。JDK 8 时代常见的讲法是“偏向锁 → 轻量级锁 → 重量级锁”，用 CAS、栈上锁记录和操作系统互斥量处理不同竞争程度。

但这不是所有现代 JDK 都固定遵循的通用流程：偏向锁在 JDK 15 被默认禁用并被标记为废弃（JEP 374）；后续 HotSpot 又持续重构对象监视器实现。Java 语言规范只承诺同步语义，不承诺 Mark Word 的具体位布局或锁升级路线。面试中可以解释 JDK 8 的经典机制，但要主动说明这是特定 HotSpot 版本的实现。

3. ReentrantLock：把锁能力变成显式 API

ReentrantLock与 synchronized都提供可重入互斥。它存在的价值不是“更快”——现代 JVM 下不能做这种笼统结论——而是提供可中断、限时尝试、公平策略、多个条件队列等更强的控制能力。

正确的基本模板

import java.util.concurrent.locks.Lock;
import java.util.concurrent.locks.ReentrantLock;

public class Inventory {
    private final Lock lock = new ReentrantLock();
    private int stock = 100;

    public boolean deduct(int quantity) {
        lock.lock();
        try {
            if (quantity <= 0 || stock < quantity) {
                return false;
            }
            stock -= quantity;
            return true;
        } finally {
            lock.unlock(); // 必须放在 finally 中
        }
    }
}

必须先成功获取锁，再进入 try。如果把 lock() 放进 try 且获取过程失败或被中断，finally 可能错误地释放一个当前线程未持有的锁。

tryLock 与可中断获取

public boolean tryDeduct(int quantity) throws InterruptedException {
    if (!lock.tryLock(200, java.util.concurrent.TimeUnit.MILLISECONDS)) {
        return false; // 超时后降级、重试或返回“系统繁忙”
    }
    try {
        if (quantity <= 0 || stock < quantity) {
            return false;
        }
        stock -= quantity;
        return true;
    } finally {
        lock.unlock();
    }
}

public void rebuildIndex() throws InterruptedException {
    lock.lockInterruptibly(); // 等锁期间能响应 interrupt
    try {
        doRebuild();
    } finally {
        lock.unlock();
    }
}

private void doRebuild() {
    // 重建本地索引
}

无参 tryLock()立即返回，适合“拿不到就做别的事”；带超时版本给等待设置上限；lockInterruptibly()允许取消长时间等待的任务。默认构造的是非公平锁；new ReentrantLock(true)创建公平锁，会优先考虑等待更久的线程，但通常吞吐更低，而且无参 tryLock()仍可直接插队。

Condition：一把锁，多种等待条件

Condition类似内置监视器的 wait/notify，但一把锁可以创建多个条件队列。下面的有界队列分别等待“非空”和“未满”，避免无关线程被一起唤醒：

import java.util.ArrayDeque;
import java.util.Queue;
import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.ReentrantLock;

public final class BoundedBuffer<E> {
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notEmpty = lock.newCondition();
    private final Condition notFull = lock.newCondition();
    private final Queue<E> queue = new ArrayDeque<>();
    private final int capacity;

    public BoundedBuffer(int capacity) {
        if (capacity <= 0) throw new IllegalArgumentException();
        this.capacity = capacity;
    }

    public void put(E element) throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (queue.size() == capacity) { // 用 while 防止虚假唤醒
                notFull.await();
            }
            queue.add(element);
            notEmpty.signal();
        } finally {
            lock.unlock();
        }
    }

    public E take() throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (queue.isEmpty()) {
                notEmpty.await();
            }
            E value = queue.remove();
            notFull.signal();
            return value;
        } finally {
            lock.unlock();
        }
    }
}

4. AQS：把“排队与唤醒”抽成并发框架

AbstractQueuedSynchronizer是 JUC 中构建同步器的基础框架。ReentrantLock、Semaphore、CountDownLatch等都复用了它。AQS 负责同步状态、等待队列、阻塞与唤醒；子类只需定义“怎样算获取成功”和“怎样释放”。

state 与两种模式

AQS 用一个 volatile int state表示同步状态，并提供基于 CAS 的读取、设置和比较更新方法。状态的含义由具体同步器决定：在 ReentrantLock中，state == 0通常表示未持有，大于 0 表示持有线程的重入次数；在 Semaphore中，它可表示剩余许可数。

  • 独占模式：同一时刻只允许一个线程成功，如 ReentrantLock。
  • 共享模式：一次释放可能让多个等待者继续，如 Semaphore、CountDownLatch。

获取失败后发生了什么

  1. 线程先调用子类实现的获取逻辑，通常通过 CAS 尝试改变 state。
  2. 失败后，AQS 将当前线程封装为节点并入队；入队本身也需要应对并发。
  3. 线程根据前驱节点和队列状态判断是否应该阻塞，随后通过 LockSupport.park挂起，而不是一直空转。
  4. 持锁线程释放时更新 state，必要时通过 LockSupport.unpark唤醒合适的后继节点。
  5. 被唤醒不代表已经获得锁，它仍需回到获取逻辑重新竞争。

ReentrantLock 如何落在 AQS 上

ReentrantLock内部通过 AQS 子类实现同步逻辑。首次获取时 CAS 将 state从 0 改为 1，并记录独占线程；同一线程再次获取就递增 state；释放时递减，为 0 才真正清空所有者并允许唤醒后继。

公平实现会在尝试占有前检查队列中是否已有更早的等待者；非公平实现允许新到线程直接参与 CAS，减少线程切换并提高吞吐，却可能让等待时间更不均匀。这里描述的是稳定的设计思想，不等同于逐行复述某个 JDK 版本的内部类源码。

5. CAS 与乐观锁

CAS（Compare-And-Swap）接收三个逻辑操作数：内存位置 V、预期值 A、新值 B。只有当 V 仍等于 A 时，才原子地把 V 更新为 B；否则返回失败，调用方可读取新值再试。

import java.util.concurrent.atomic.AtomicInteger;

public class RequestMetrics {
    private final AtomicInteger activeRequests = new AtomicInteger();

    public void onStart() {
        activeRequests.incrementAndGet();
    }

    public void onFinish() {
        activeRequests.decrementAndGet();
    }

    public int current() {
        return activeRequests.get();
    }
}

原子类内部以 CAS 为核心，避免了传统互斥锁的排队与线程挂起成本。但“无锁”不等于“无成本”：高竞争下大量 CAS 失败会反复消耗 CPU；单变量原子也无法自动维护多个字段之间的不变式。热点计数场景还可考虑 LongAdder，用分散竞争换取更高吞吐，但它的瞬时求和不适合作为强一致控制条件。

ABA 问题

如果值从 A 变成 B 又变回 A，普通 CAS 只看当前值，会误以为它从未改变。当“变化过程”本身有业务意义时，可把版本号一起比较：

import java.util.concurrent.atomic.AtomicStampedReference;

public class VersionedReferenceDemo {
    public static void main(String[] args) {
        AtomicStampedReference<String> ref =
                new AtomicStampedReference<>("A", 0);

        int stamp = ref.getStamp();
        String value = ref.getReference();

        boolean updated = ref.compareAndSet(
                value, "B",
                stamp, stamp + 1
        );
        System.out.println(updated); // true
    }
}

AtomicStampedReference让引用与版本戳同时参与比较。不过涉及复杂对象状态、数据库数据或跨服务更新时，版本列、事务条件更新或分布式一致性协议通常更合适。

6. volatile 与锁的关系

volatile解决的是“某个线程的写入何时对其他线程可见”以及特定的重排序约束。对 volatile 变量的写 happens-before 随后对该变量的读，因此它适合发布状态和停止标记。

public class GracefulWorker implements Runnable {
    private volatile boolean running = true;

    public void shutdown() {
        running = false;
    }

    @Override
    public void run() {
        while (running) {
            doOneTask();
        }
    }

    private void doOneTask() {
        // 处理一个足够短、能及时退出的任务
    }
}

但 volatile int count仍不能让 count++变成原子操作。volatile 保证每次读写本身的可见性，却不能阻止两个线程都读到 7、都计算出 8、再分别写入 8。复合操作需要锁、AtomicInteger.incrementAndGet()或其他原子协议。

可见性保证 volatile 读写的可见性同一锁的释放—获取建立可见性
有序性限制相关内存操作重排临界区边界建立 happens-before

在 CAS 算法里，常用 volatile 让线程读到最新状态，再用 CAS 保证条件更新的原子性。适合 volatile 的典型条件是：写入不依赖旧值，或始终只有一个写线程；变量用于状态发布，而不是维护跨字段约束。

7. ReadWriteLock 与 StampedLock

互斥锁会让所有访问串行化，但很多缓存与配置对象是“读多写少”。读写锁把访问分为共享读和独占写：多个读锁可以共存；写锁与读锁、其他写锁都互斥。

ReentrantReadWriteLock

import java.util.HashMap;
import java.util.Map;
import java.util.concurrent.locks.Lock;
import java.util.concurrent.locks.ReentrantReadWriteLock;

public final class LocalCache<K, V> {
    private final Map<K, V> data = new HashMap<>();
    private final ReentrantReadWriteLock rw =
            new ReentrantReadWriteLock();
    private final Lock readLock = rw.readLock();
    private final Lock writeLock = rw.writeLock();

    public V get(K key) {
        readLock.lock();
        try {
            return data.get(key);
        } finally {
            readLock.unlock();
        }
    }

    public void put(K key, V value) {
        writeLock.lock();
        try {
            data.put(key, value);
        } finally {
            writeLock.unlock();
        }
    }
}

读写锁不是读多场景的自动加速器。临界区很短、线程少或写入频繁时，额外的状态维护可能得不偿失。单纯的并发 Map 访问优先考虑 ConcurrentHashMap；只有需要跨多步读取快照或复合更新时，外部读写锁才更有价值。

StampedLock 的乐观读

import java.util.concurrent.locks.StampedLock;

public final class Point {
    private double x;
    private double y;
    private final StampedLock lock = new StampedLock();

    public double distanceFromOrigin() {
        long stamp = lock.tryOptimisticRead();
        double currentX = x;
        double currentY = y;
        if (!lock.validate(stamp)) {
            stamp = lock.readLock();
            try {
                currentX = x;
                currentY = y;
            } finally {
                lock.unlockRead(stamp);
            }
        }
        return Math.hypot(currentX, currentY);
    }

    public void move(double deltaX, double deltaY) {
        long stamp = lock.writeLock();
        try {
            x += deltaX;
            y += deltaY;
        } finally {
            lock.unlockWrite(stamp);
        }
    }
}

乐观读阶段并没有真正持有读锁，所以必须先把需要的字段复制到局部变量，再调用 validate；验证失败则退化为悲观读锁。StampedLock不可重入，stamp 必须与解锁方式匹配，也不提供 Condition。错误复用 stamp 或在持锁方法中递归调用，很容易造成永久等待。只有基准测试证明读竞争明显时，才值得为它增加复杂度。

8. 实际开发中的锁选择

选并发工具时，先问三个问题：状态是否真的共享？正确性是否跨多个变量或步骤？竞争发生在单 JVM、数据库，还是多个服务实例之间？工具要与并发边界一致。

01

并发计数器

只需单变量原子增减，用 AtomicInteger/AtomicLong；高并发指标累加可用 LongAdder。如果“计数达到阈值后更新状态”必须作为整体完成，就使用锁或 CAS 状态机。

02

本地缓存

单项查询与更新优先 ConcurrentHashMap及其 computeIfAbsent。需要一致快照或批量替换时，考虑不可变快照 + volatile 引用，或 ReentrantReadWriteLock。

03

共享资源更新

临界区小、无需特殊等待能力时优先 synchronized，语义直接且异常安全。需要超时、取消、公平策略或多个条件队列时用 ReentrantLock。

04

库存扣减

单 JVM 内存库存可由锁或原子变量保护；真实库存通常在数据库中，应使用事务与条件更新（例如 UPDATE ... WHERE stock >= ?）、行锁或版本号。JVM 锁不能协调多个应用实例。

05

任务状态管理

简单停止标记可用 volatile；状态迁移用 AtomicReference.compareAndSet建立合法转换；多个字段需要一致更新时使用锁封装完整状态机。

06

线程安全集合

优先选择 ConcurrentHashMap、BlockingQueue、CopyOnWriteArrayList等成熟容器。不要在已有原子复合 API 外再套大锁，除非业务要求跨多次操作保持一致。

四种并发边界，不要混用

机制协调范围典型用途不能替代什么
JVM 本地锁同一进程内线程保护内存对象不能协调另一台机器上的实例
数据库事务数据库定义的事务边界多条数据操作的 ACID不能自动保护 JVM 内存
数据库行锁访问同一数据库记录的事务库存、余额等记录更新不等于跨资源的分布式协调
分布式锁共享协调服务覆盖的多个实例跨实例互斥任务不能替代事务；还要处理租约、续期、故障与 fencing token
关于“库存加一把 ReentrantLock”

它只在请求全部落到同一 JVM 时有效。服务水平扩展后，每个实例都有自己的锁。数据库条件更新、事务隔离或带 fencing token 的分布式协调，才是跨实例问题的对应工具。

9. 死锁：锁都没坏，系统却不再前进

死锁通常满足互斥、持有并等待、不可剥夺、循环等待四个条件。工程上最有效的做法不是运行后检测，而是从设计上破坏条件：

  • 所有路径按固定顺序获取多把锁，例如按账户 ID 从小到大加锁。
  • 缩小临界区，不要持锁执行远程调用、阻塞 I/O 或用户回调。
  • 用 tryLock(timeout)设置等待上限，并在失败时完整回滚已获得的锁。
  • 减少嵌套锁；能用并发容器、消息队列或单线程串行化解决时，不自行拼装复杂协议。
  • 线上结合线程 dump 观察 BLOCKED线程与锁依赖关系。

10. Java 锁常见面试问题

下面的“直接回答”控制在面试口述长度；展开项用于追问时补充。

01synchronized 和 ReentrantLock 有什么区别？

直接回答：两者都是可重入互斥锁。synchronized 由 JVM 管理释放，语法简单且异常安全；ReentrantLock 基于 JUC/AQS，需要 finally 手动 unlock，但支持可中断等待、tryLock、超时、公平策略和多个 Condition。

关键点：不要笼统说 ReentrantLock 一定更快。选型主要看控制能力、可维护性和实测竞争情况。

02synchronized 是可重入锁吗？

直接回答：是。同一线程拿到某对象的监视器后，可以再次进入由同一监视器保护的同步代码。运行时记录持有线程和重入次数，每退出一层减一次。

关键点：重入针对“同一线程 + 同一监视器”，不是任意锁。

03synchronized 锁住的是什么？

直接回答：锁的是对象关联的监视器。实例同步方法锁 this，静态同步方法锁对应的 Class 对象，同步块锁括号中的对象。

关键点：是否互斥取决于锁对象是否相同，而不是代码看起来是否相同。

04synchronized 底层是如何实现的？

直接回答：同步块通常通过 monitorenter/monitorexit 字节码表达，同步方法通过 ACC_SYNCHRONIZED 标志表达，JVM 结合对象监视器完成所有权、等待和唤醒，并在解锁—加锁之间建立 happens-before。

深入补充：Mark Word、轻量级锁等是特定 HotSpot/JDK 版本的优化实现。JDK 8 的经典锁状态不能无条件套用到所有现代 JDK；偏向锁从 JDK 15 起默认禁用并废弃。

05什么是 AQS？

直接回答：AQS 是构建同步器的框架，用 volatile state 表示同步状态，以 CAS 更新状态，并管理获取失败线程的等待队列以及 park/unpark。子类定义获取和释放规则。

关键点：支持独占与共享两种模式；ReentrantLock、Semaphore、CountDownLatch 都复用了它。

06ReentrantLock 为什么能够实现公平锁？

直接回答：公平实现尝试获取锁前，会检查 AQS 队列中是否已有等待更久的前驱；有前驱就先排队。非公平实现允许新线程直接竞争 CAS。

关键点：公平是调度倾向，不是绝对实时保证；公平锁通常会增加切换、降低吞吐。无参 tryLock 也不遵循公平顺序。

07CAS 是什么？有什么缺点？

直接回答：CAS 原子比较内存值 V 是否等于预期 A，相等才写入 B。它避免了传统互斥等待，但高竞争会持续重试消耗 CPU，还存在 ABA 问题，并且单次 CAS 很难直接维护多个变量的不变式。

关键点：ABA 可通过版本戳缓解；复杂状态通常封装成不可变对象后 CAS 整体引用，或直接用锁。

08volatile 能保证线程安全吗？

直接回答：不能一概而论。volatile 保证可见性并约束相关重排序，但不保证 count++ 这类复合操作的原子性。简单状态标记、单写多读发布场景可以安全使用。

关键点：判断依据是操作是否依赖旧值、是否有多个写者、是否存在跨字段不变式。

09synchronized 和 volatile 有什么区别？

直接回答：volatile 是变量级的可见性与有序性工具，不提供互斥；synchronized 通过同一监视器的互斥保护复合操作，同时建立可见性与有序性保证。

关键点：volatile 读写不会因为锁竞争挂起线程，但能力也更窄。

10什么情况下应该使用读写锁？

直接回答：共享数据读操作明显多于写操作、读临界区有一定成本，并且并发读能带来实际收益时考虑读写锁。写频繁或临界区很短时，普通互斥锁可能更好。

关键点：优先评估 ConcurrentHashMap 等并发容器，用基准测试验证收益。

11什么是死锁？如何避免？

直接回答：死锁是多个线程各自持有资源并等待对方释放，形成循环等待，导致都无法继续。常用避免方式是固定加锁顺序、减少嵌套锁、缩小临界区，以及用 tryLock 超时退出。

关键点：不要持锁做网络 I/O；线上可用线程 dump 排查锁等待环。

12Java 中如何选择合适的锁？

直接回答：先确定并发边界和要维护的不变式。简单临界区用 synchronized；需要超时、中断或 Condition 用 ReentrantLock；单变量原子更新用 Atomic 类；状态发布用 volatile；读多写少且复合读取用读写锁；集合操作优先并发容器。

关键点：单 JVM 锁不能解决多实例并发；数据库数据要结合事务、条件更新或行锁，跨实例协调才考虑分布式锁。

结语：锁的本质是约束访问协议

理解锁，不应停在 API 对照表。真正重要的是辨认共享状态、划清一致性边界，并知道工具提供了哪种 happens-before 关系。synchronized适合表达简单而可靠的互斥；ReentrantLock提供更可控的等待协议；AQS 复用了排队与唤醒；CAS 和 volatile 则支撑更细粒度的无锁协作。

工程中最好的锁往往是范围最小、语义最直接、能被团队稳定维护的那一个。遇到跨 JVM、跨数据库或跨服务问题时，也要及时离开“Java 锁”的思维边界，选择真正覆盖共享资源的协调机制。
