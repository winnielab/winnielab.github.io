Claude Code 团队如何做代码审查：
用分层自动化换取人类注意力

当代理生成的代码让变更量成倍增长，逐行人工审查不再可扩展。Claude Code 团队的答案不是取消审查，而是把验证前移、让自动化承担大部分阅读，再依据风险把真正需要判断与担责的部分交给人。

译编说明

本文根据 Addy Osmani 发布的英文长文整理翻译，保留主要论点、关键数据与实施清单，并按中文技术文章的阅读习惯重组结构；它不是逐句直译，也不是 Anthropic 或 Claude Code 的官方中文版本。完整来源与声明见文末。

1. 重新定义代码审查：不是“谁读过”，而是“什么会出错”

Claude 曾被披露承担 Claude Code 约 90% 的代码编写工作。随之而来的问题很直接：代码产出速度上升后，谁还能逐行读完所有变更？如果代码出错，又该由什么机制兜底？

原文给出了一组很有代表性的结果：从 6 月到 9 月，Claude Code 代码库合并的拉取请求数量增长到两倍以上，而需要回滚的拉取请求占比反而下降了 40% 以上。团队并没有停止代码审查，而是自动化了大部分“阅读”，同时显著增强了验证与回滚能力。

01

审查前移

代理在 PR 创建前运行测试、构建与界面验证，并让一个拥有全新上下文的子代理先检查差异。

02

层层过滤

AI 审查、安全审查、CI、人类审批和合并队列分别捕获不同类型的问题。

03

快速恢复

功能开关、分阶段发布与一键回滚承认“漏网之鱼一定存在”，并限制其影响范围。

传统审查经常把“有人读过代码”当成完成标准。Claude Code 团队换了一个问题：这个变更可能在哪里出错，最合适的自动化或人工检查是什么？这也改变了审查的时机——它不再是代码写完后的单一闸门，而更像写作时持续运行的拼写检查。

代码审查仍承担两个目标：一是上线前发现并修复缺陷，二是帮助团队建立对代码库的共同理解。原文主要讨论第一个目标，但后文也回应了“机器读完大部分代码后，人如何继续学习系统”的问题。

2. 真正要优化的是人类时间，而不只是审批次数

人类时间有两面成本：一面是花在审查上的时间，另一面是糟糕代码进入系统后花在修复上的时间。如果只是减少前者，却让事故和回滚增加，就不是节省，只是把成本挪到了更晚、更昂贵的位置。

团队的目标是：Claude Code 的 CLI、桌面端、Web 端和移动端仓库中，大多数拉取请求最多只需要一名人类参与——这名人也可以是作者本人——同时不提高回滚率或事故率。

指标类型具体指标作用
人力投入每个 PR 的人类审批中位数与 P95观察常态与长尾成本
协作摩擦人类评论数、等待人工处理的时间定位流程中的排队与往返
质量护栏回滚率、事故率防止“减少审查”只是把成本后移
规模背景

Anthropic 的单体仓库在同年 5 月约有 2,500 个变更每天合入，到 9 月已超过 30,000 个。Claude Code 本身不在这个单体仓库中，但承受着类似的速度压力。这样的吞吐量下，逐行、同步、纯人工的审查方式很难继续扩展。

3. 一次变更的旅程：多层防线，而不是一道闸门

一个典型变更会从工程师电脑或 Slack 中的 Claude 会话出发，依次经过提交前验证、PR 级审查、合并与发布。大部分流程自动完成，人类注意力只集中到高风险决策上。

第一层：PR 创建前就完成验证

团队要求代理交付可验证的结果，而不只是说“任务完成了”。验证可以是测试、构建、lint，也可以是在浏览器或手机模拟器中运行界面，并把结果展示出来。随后再由一个拥有全新上下文的子代理审查差异。

许多工程师还会运行内部技能来寻找缺陷、缩减无关 diff、做端到端验证，或根据设计规范检查 UI。Boris Cherny 估计，为代理配备明确的验证流程，能让输出质量提升约 2～3 倍。

重复出现的问题不应只在每个 PR 里反复提醒，而要回到源头修复：更新技能、增加 lint 规则，或改进项目文档。原文特别提到两个文件：

  • CLAUDE.md：简要描述技术栈、约定、目标与非目标，为每次审查提供稳定上下文；大型代码库只保留入口信息，再链接到详细文档。
  • REVIEW.md：由代码所有者说明本模块真正重要的审查点，例如如何定义失败、哪些路径忽略、如何减少无意义挑错，以及发现必须附带文件与行号。

第二层：每个 PR 都经过 AI 审查

每个拉取请求都会先由 Claude 对照整个代码库和作者陈述的意图进行审查：变更是否真的解决问题、是否与更大系统契合、是否破坏其他部分；遇到缺陷修复时，审查器还会尝试追到根因。

从研究预览发布到原文写作时，收到实质性审查意见的内部 PR 占比从 16% 上升到 54%。超过 1,000 行的 PR 中，多数能检出问题；较小的 PR 则多数返回无问题。仓库管理员还可以按场景选择 Quick、Standard 或 Deep 模式。

在意见展示给人之前，多名代理并行找缺陷，另一组代理对结论投票，过滤掉误报和纯样式、诊断或清理类意见。剩余发现会按严重程度排序，并标注为 Important、Nit 或 Pre-existing。所有发现都必须被修复，或由作者给出理由后关闭线程。

第三、四层：可阻塞的安全审查与 CI

安全审查是独立的一道自动化检查。只要代码审查或安全审查仍有未处理发现，PR 就不能合并；后续提交修复问题时，相应发现可以自动关闭。

常规 CI 则覆盖 lint、类型检查、多平台测试、构建与打包。一个 CLI PR 在任何人打开前就可能运行数十项检查。PR 模板要求说明“如何测试”“风险是什么”“如何回滚”；Claude 可以代为填写，但作者仍要负责核对。

第五层：按变更风险决定人类审批强度

审批等级由变更本身决定，而不是由作者名气决定。分类器根据代码差异判断风险，另一个分类器还会确认某个具体变更是否需要额外审批。敏感路径与 CI 工作流始终需要人类参与。

宽松路径只开放给仓库的可信作者，通常就是负责该仓库的团队。代理的批准不能充当人类批准。作者要对变更负责：如果 PR 由代理编写，代理的操作者仍计为责任人。审批只对当前提交有效；代理推送新提交，或有人手工解决冲突后，原审批会失效并要求重新确认。

第六层与最后防线：合并队列、渐进发布和快速回滚

合并队列会把变更应用到最新的 main 后重新运行检查，防止两个各自通过测试的 PR 合并后一起破坏主干。新功能通常先放在功能开关后，只对 Anthropic 员工开放；公开发布时先进入 latest 渠道，stable 渠道延后。

坏变更仍可能穿透所有检查，因此最后一层是快速反馈与恢复：关闭功能开关无需重新部署；值班轮换、内部高频使用、遥测和回滚仪表盘负责尽快暴露回归。事故复盘关注“哪一层原本应该捕获它”，而不是只追问谁提交了代码。

4. 让审查器持续变好：用真实事故做评测

团队把曾导致事故的 PR、修复提交与回滚收集起来，由熟悉代码库的工程师确认缺陷位置和结论，再让审查系统每天在这组案例上运行。每次修改审查提示、工具或模型，都要重新跑完整集合，只有分数改善才保留。

只追求“发现更多问题”会制造大量误报，因此噪声也要测量。团队观察人类如何处理每条评论：修复、拒绝、说明这是有意设计，还是认为它无关紧要；同时在已知干净的 PR 上运行审查，检查系统是否提出反而会伤害代码的修改。

审查必须收敛

代理作者与代理审查者可能陷入无限往返。团队曾发现一个 CLI 项目的 PR 在一夜之间循环了 50 多次。追溯审查器反复指出的代码后发现，约 59% 从第一次审查起就已经存在——系统并非不断发现新引入的缺陷，而是在每一轮多找出几个历史问题。

他们据此调整复审策略：限制轮数，三轮后要求作者重新评估方案；初始几轮之后只检查新的差异；一次性说明问题类别，让作者成批修正；避免重复报告已经出现过的意见。同时，审查代理会在夜间扫描当前代码库，把历史问题提前从 PR 流程中分离出去。

5. 人类仍然不可替代，但要把注意力用在正确的地方

让资深工程师为常见错误停下手头工作，成本远高于把这种检查自动化。人类审查者仍然负责机器难以代替的事情：

  • 决定是否值得做：设定产品愿景、审美、目标与边界，而不只是检查实现是否自洽。
  • 审计危险代码：认证、计费、自动更新、CI、发布流程和安装器等高影响区域。
  • 审查架构：架构选择会成为后来者遵循的约定，影响远超当前 diff。
  • 验证证据：检查测试输出、运行命令、截图和审查结论，而不是只点一个赞。
  • 承担责任：无论代码由谁敲出，每个上线变更都必须有一个人对其结果负责。

如果机器负责阅读，人如何理解代码库？

代码审查长期以来也是传播上下文的渠道。Claude Code 团队没有要求任何人把整个代码库装进脑中；当成员需要理解某个局部时，会让 Claude 针对那一小块生成最新的讲解，一些人还会进一步生成可交互的小型可视化。

这不是否认共享知识的重要性，而是改变获取知识的单位：从“读完每个 diff”改成“在需要时理解准确的系统切片”。团队也默认在开放 Slack 频道中工作，让其他人能看到正在进行的设计和实现，并随时加入讨论。

6. “你合入，你负责”与尽早转向

如果一个小型或中型变更出问题，通常由合并它的人修复，因为这个人掌握最多上下文。这个机制之所以不会演变成追责游戏，依赖几个前提：变更足够小、易于审查和回滚；功能开关与分阶段发布能在几分钟内缩小影响；高风险代码要求更高验证标准；遥测和内部使用能快速暴露回归；事故复盘关注系统而非归咎个人。

代理让“开始写一份新实现”变得便宜，因此放弃错误方案也应该同样自然。有人在讨论中指出方向不对时，作者可以直接关闭 PR 或修改方案，而不必因为已经生成了大量代码就产生沉没成本。关键是尽早在讨论中转向，不要等到实现定型后才留下阻塞性意见。

7. 如何把这套方法落到自己的团队

原文给出的实施路径可以整理为四组清单。重点不是一次性复制整套系统，而是先建立验证与质量护栏，再用数据逐步放宽低风险路径。

01

提交 PR 之前

在简短的 CLAUDE.md 中列出代理可执行的检查；通过 hooks 调用格式化与 lint；用全新上下文审查变更；用 REVIEW.md 记录反复出现的问题。

02

每个 PR 上

强制 CI；在模板中加入 Testing、Risk 与 How to revert；接入 AI 与安全审查；要求所有审查线程在合并前解决。

03

审批阶段

按变更而非作者定义风险；从严格规则开始，再用证据逐步放宽；机器人批准不计入必需的人类批准；新提交到达后撤销旧批准。

04

合并与上线后

使用合并队列、功能开关、内部先行和分阶段发布；提供一步回滚；持续记录事故与回滚，审查器变化后重跑评测。

两个容易漏掉的约束

第一，审查强度要与影响半径匹配：日常改动可以快，认证、计费、CI 与发布路径必须保留人类把关。第二，复审轮次必须有上限，否则代理作者与代理审查者可能在低价值意见上无限循环。

8. 结语：从“人读每一行”转向“系统覆盖每种风险”

Claude Code 团队的方法并不等于“让 AI 自己批准自己”。它把代码审查拆成多个各有所长的环节：代理在编写时验证，多个审查器在 PR 上找缺陷，安全审查与 CI 阻塞明确风险，人类按影响半径介入，合并队列与分阶段发布降低上线风险，最后再用遥测与回滚承认任何系统都不可能百分之百拦截错误。

这套实践真正优化的是每次变更所需的人类努力，质量底线则由回滚率和事故率守住。每当审查器漏掉问题，团队就追问缺少了什么上下文，并把答案写入 CLAUDE.md、技能或新的自动检查。审查不再是一场一次性的阅读仪式，而是一个能从失败中学习、持续演化的工程系统。
